# TERRITORY — Specification

**Version:** 0.1  
**Status:** Playable local vertical slice; online design target  
**Last synchronized with:** application 0.1.0, map version 1, protocol draft 1

This is the canonical description of what Territory is, how a match works, and which technical contracts must hold. [ARCHITECTURE.md](ARCHITECTURE.md) explains the current code; this document explains the intent.

---

## 1. Product definition

### 1.1 One-line pitch

A fast, readable territory war played on a very large pixel atlas, where every pixel can change hands and every outcome can be replayed.

### 1.2 Reference point

OpenFront is the closest genre reference: a browser strategy game with a huge pixel territory map, real-time expansion, and rival states. Territory is not a clone and does not reuse OpenFront assets or code. It uses an original procedural map, rules, presentation, and simulation model.

### 1.3 Design pillars

1. **The map is the game.** Ownership is expressed at pixel resolution. Territory growth must be visibly satisfying at combat zoom and readable at world zoom.
2. **Determinism is a feature.** A seed plus a command log must be sufficient to reproduce a match. Networked clients and the server must agree bit-for-bit on simulation state.
3. **Speed is a feature.** A tick must not stall the renderer; a territory change must not upload the whole map. Budgets are explicit and measured.
4. **Readable conflict.** A player should understand within a second who owns a region, where their frontier is, and what a click will do.
5. **Online-ready boundaries.** Even while local-only, simulation, rendering, and UI communicate through contracts that a server can adopt without a rewrite.

### 1.4 Match shape (target)

- 8 states: one human commander and seven bots in the local slice; all human later.
- One shared 2048 × 1024 atlas, approximately 38% land.
- Fixed 10 Hz simulation, real-time.
- Target match length: roughly 4–10 minutes for a decisive game, tuned through economy and bot aggression.
- No build queues, unit micro, or card systems. Troops are generated by land and spent on map expansion.
- Win by being the last state with at least one owned pixel.

## 3. Vocabulary

| Term                 | Meaning                                                                                             |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| **Cell / map pixel** | One element of the 2048 × 1024 ownership grid                                                       |
| **Owner**            | Player id `1..8`; `0` means unclaimed                                                               |
| **Territory**        | Count of land cells owned by a player                                                               |
| **Frontier**         | An owned land cell with at least one adjacent land cell owned by someone else (including unclaimed) |
| **Attack**           | A deterministic local BFS front that converts target-owned cells to the attacker                    |
| **Tick**             | One fixed simulation step, 100 ms apart                                                             |
| **Command**          | An intent (currently only attack) applied at a tick boundary                                        |
| **Snapshot**         | Read-only UI view of the simulation state, produced after a tick                                    |
| **Change batch**     | Packed owner/index words emitted for the renderer                                                   |
| **Seed**             | A 32-bit value that regenerates the exact same world                                                |
| **Bot**              | A server/local deterministic AI player                                                              |

## 4. Rules of a match

All numeric rules live in `src/lib/game/constants.ts`. If a value there changes in a way that affects outcomes, increment the protocol/map version and update this section.

### 4.1 The world

- Dimensions: **2048 × 1024** cells (2,097,152 total).
- The generator targets **38% land** using a deterministic height histogram, with ocean at the map edges.
- Each cell has a static binary land mask and an 8-bit terrain shade value used for height texture and contours.
- Ocean can never be owned.
- Map generation is deterministic from the seed, but is versioned by `MAP_VERSION`. A different generator with the same seed is a different map.

### 4.2 Starting positions

- Eight start points are chosen by deterministic farthest-point sampling from high-density land candidates, biased toward the map centre for the first pick.
- Starts are separated so the initial beachheads do not overlap.
- A starting territory is a ragged disc of radius approximately **26 cells**, clipped to land, with deterministic per-cell frontier wobble.
- Every player starts with **4,000 troops** and zero income until `step()` calculates the first tick. All players are equal at spawn.

### 4.3 Troop economy

- **Income per tick:** `2 + floor(territory / 100)`.
- The HUD displays this value multiplied by `TICK_RATE` as income per second.
- **Troop cap:** `2,000 + territory × 3`.
- Troops are integers. There is no fractional army or hidden upkeep.
- Land is the only economy: losing land immediately reduces both income and cap.

### 4.4 Attack lifecycle

1. The player clicks a cell. `enqueueAttack` validates it against current state for immediate UI feedback.
2. If valid, an attack command is queued and applied at the start of the next tick.
3. The clicked cell's current owner is the **target owner** (a rival or `0` / neutral).
4. The simulation searches within a **34-cell radius** for cells of the target owner that are adjacent to the attacker's territory. These become attack seeds. Seeds are sorted by squared distance from the click, then by index, and capped at 96.
5. Launching costs **50 troops** and is refused if the attacker has fewer than 51. Up to **3 attacks** may be active per player.
6. Each tick, an attack visits its BFS queue and captures up to **30** valid target-owned cells. Every captured cell costs **1 troop**.
7. Capturing a cell enqueues its four neighbours if they still belong to the same target owner, are land, and have not been seen. This means an attack flows through connected enemy territory and stops at oceans or other owners.
8. An attack is complete when its queue is exhausted or its troops are exhausted. Troop exhaustion pauses the front; if troops later regenerate (because the player still earns income), the same attack can resume on later ticks.
9. Attacks are processed in ascending creation id. If one attack takes the cell another wanted, the later attack simply skips it.
10. Multiple attacks from the same player can compete for the same target, so commands are not a promise of a particular pixel.

### 4.5 Valid attack clicks

An attack is valid only if all are true:

- The match has not ended.
- The attacker is alive.
- The clicked coordinate is inside the map and on land.
- The clicked cell is not owned by the attacker.
- The attacker has fewer than 3 active attacks.
- The attacker has at least `ATTACK_LAUNCH_COST + 1` troops.
- At least one attack seed exists: a cell owned by the clicked cell's owner, within 34 cells, adjacent to the attacker's territory.

The UI reports concrete reasons: ocean, own territory, no shared border, attack limit, no troops, eliminated, or match over.

### 4.6 Borders

- A cell is a frontier if it is owned land and has at least one adjacent land cell owned by a different owner (unclaimed land counts).
- Each player's `Set<number>` frontier is derived state, not authoritative wire state. It is maintained incrementally when ownership changes and rebuilt at spawn.
- A frontier does not include a purely coastal cell whose four land neighbours are all friendly or ocean. Ocean is not attackable.

### 4.7 Elimination and victory

- A player with zero owned land is eliminated immediately after the attack phase.
- Eliminated players stop earning income, lose troop access, and their active attacks are dropped.
- The last living player wins. The match ends and stops advancing ticks.
- If the human is eliminated first, the local UI pauses and offers spectating, rematch, or a new world. Spectating resumes the simulation until another state wins.

### 4.8 Bots

- Bots act once per second (`BOT_DECISION_INTERVAL = 10` ticks).
- Each bot with at least **700 troops** and fewer than **2 active attacks** may launch one attack per decision.
- It samples its frontier deterministically, looks for an adjacent land cell owned by someone else, and attacks. If neutral and hostile neighbours are both available, it chooses neutral 68% of the time.
- Bots do not cheat: they use the same attack API, costs, and caps as the human.
- Bots use the one simulation PRNG, in ascending player-id order, so bot behavior is replayable.

### 4.9 Order of operations inside a tick

When the match is live:

1. Increment `tick`.
2. Apply queued attack commands in `(sequence, playerId)` order.
3. Apply income and troop caps for all living players.
4. Run bot decisions (only every 10th tick).
5. Process active attacks in creation-id order.
6. Eliminate states with no territory and remove their attacks.
7. Check victory.
8. Build the public snapshot.

The exact order is part of the protocol. Changing it can change outcomes.

### 4.10 Current absence of randomness in combat

Combat has no dice, crits, spread, or morale. Given the same starting state and the same accepted commands, every pixel outcome is fixed. This is deliberate and should not be sacrificed for "feel" without an explicit determinism review.

## 5. Player experience

### 5.1 Screen flow

1. **Boot / loading:** map generation and WebGPU initialization.
2. **Intro:** game identity, world seed, optional seed load, deploy action. The simulation is paused.
3. **Live match:** HUD, map, leaderboard, war feed, minimap, status console, map tools.
4. **Paused:** badge shown; fixed ticks stop; camera still works.
5. **Defeat:** human has no territory; spectate, rematch same seed, or new world.
6. **Result:** last state wins; final standings and match stats; rematch or new world.
7. **Field manual:** accessible from the live HUD and the result screen. Explains loop, orders, camera, and system.
8. **WebGPU unavailable:** explicit error screen with reason and support guidance.

### 5.2 HUD content

- Brand / build identity.
- Human commander, army, income per second, land share, living-state rank.
- War clock.
- Pause/resume, field manual, new world.
- World-control leaderboard for all states, sorted by alive, then territory, then id.
- War feed for elimination and victory events.
- World claimed meter.
- Minimap with current camera rectangle.
- Status console: grid coordinate, hover ownership, attack orders used.
- Map tools: zoom in/out, fit, focus human.
- Key hints.
- Performance readout in the map tools: FPS and uploaded pixels/second.

### 5.3 Controls

| Input          | Behavior                                            |
| -------------- | --------------------------------------------------- |
| Left click/tap | Issue an attack if valid; otherwise explain why not |
| Left drag      | Pan camera; a drag does not fire an attack          |
| Wheel          | Zoom at the pointer                                 |
| Space          | Pause/resume when no modal input is focused         |
| `F`            | Fit map                                             |
| `C`            | Focus human beachhead                               |
| `+` / `−`      | Zoom                                                |
| `H`            | Field manual                                        |
| Minimap click  | Center camera at that world position                |

### 5.4 Camera

- Default: centered on the human start at **3.1×** fit zoom.
- Zoom range: 0.82× to 18× of the fit-to-viewport scale.
- Center is clamped so the camera cannot wander into an empty void at high zoom.
- Screen coordinates are CSS pixels; rendering accounts for devicePixelRatio (capped at 2).
- Pausing or interacting with UI must not move the camera unexpectedly.

### 5.5 Feedback rules

- Valid order: toast with the order description.
- Invalid order: toast with a specific reason.
- Attack markers are drawn on the minimap for human attacks.
- Elimination and victory events appear in the war feed.
- Hover cell is outlined by the shader; status console names the owner and explains the target type.
- Paused clicks must not issue orders.

### 5.6 Accessibility and responsive behavior

- Buttons have labels and visible focus states.
- `prefers-reduced-motion` reduces animations.
- Desktop layout: topbar, right rail (leaderboard + feed), bottom-left minimap, bottom console, bottom-right tools.
- Narrow layout: right rail and key hints collapse; topbar compresses; minimap and console shrink. Touch pan/tap work.
- Pinch zoom is not implemented in v0.1 and must be added before claiming mobile parity.

## 6. Technical contracts

### 6.1 Layer boundaries

| Layer            | May read                               | May mutate                                   | Must not do                                             |
| ---------------- | -------------------------------------- | -------------------------------------------- | ------------------------------------------------------- |
| Simulation       | constants, map, RNG                    | world state, players, attacks, change buffer | DOM, `Date`, `performance`, `Math.random`, renderer, UI |
| Renderer         | simulation arrays + change batch       | CPU control texture, GPU resources, camera   | Mutate owners/troops/attacks                            |
| UI / GameCanvas  | snapshots, camera bridge               | local presentation state                     | Mutate ownership directly                               |
| Network (future) | protocol intents, snapshots, checksums | authoritative command queue                  | Trust a client's state                                  |

### 6.2 Fixed-step driver

- Loop: `requestAnimationFrame` accumulates elapsed time with a 250 ms catch-up cap.
- At most 4 simulation steps are executed per rendered frame.
- If 4 steps are consumed, the accumulator resets instead of spiraling.
- Paused or ended matches do not advance ticks.
- The simulation never reads the clock; only the driver does. This is essential for determinism and replay.

### 6.3 Snapshot boundary

- The UI receives a `GameSnapshot` after each tick.
- Snapshot values are primitives/arrays suitable for Svelte reactive state.
- The snapshot does not expose mutable simulation arrays.
- The renderer is driven directly by the change batch, not forced to diff snapshots.

### 6.4 Change batch

- Type: `Uint32Array`, capacity 16,384 words.
- Packing: `(owner << 21) | pixelIndex`.
- Owner occupies the high bits because the map has exactly 2²¹ pixels.
- The batch is only valid until the next `step()`; the driver consumes it immediately.
- If the buffer overflows, the renderer is instructed to perform a full texture resync. Overflow must never alter game state.

### 6.5 Map and versioning

- Map dimensions are fixed at 2048 × 1024 in v0.1. Custom dimensions are rejected by the simulation constructor.
- `MAP_VERSION` identifies the generator. Seed alone is not enough across versions.
- Map generation uses integer lattice hashes and IEEE arithmetic for interpolation. It is deterministic in practice on conforming JS engines; because it is versioned, a generator rewrite is intentional.

## 7. Determinism contract (summary)

The full contract is in [DETERMINISM.md](DETERMINISM.md). Normative points:

1. **Same simulation build, map version, seed, and ordered commands ⇒ same state and checksum.**
2. No simulation decision may depend on wall-clock time, frame rate, camera, device, UI, or unseeded randomness.
3. All authoritative arithmetic is integer: troops, territory, pixel ownership, and attack limits.
4. The PRNG is seeded and draw order is fixed. Adding or removing a draw changes bot behavior.
5. Commands apply at tick boundaries, not immediately mid-tick.
6. Command ordering is explicit and stable.
7. Checksums cover owners, tick, RNG state, attacks, players, and winner.
8. Any behavior change to the above requires a protocol-version decision and new determinism tests.

## 8. Rendering contract (summary)

Full detail is in [RENDERING.md](RENDERING.md). Normative points:

1. The map is one 2048 × 1024 `rgba8unorm` control texture plus a 256 × 1 palette texture, sampled with nearest filtering.
2. The control texture stores: owner id in R, land mask in G, terrain shade in B, unused alpha.
3. Per-tick changes are uploaded as dirty 64 × 64 tiles, with adjacent dirty tiles merged into horizontal strips. Never do a full-map upload per tick during normal play.
4. A full upload is allowed only on initial load, renderer resync, GPU loss, or a change-buffer overflow.
5. A full-screen triangle and one fragment shader perform all map coloring, borders, coastlines, ocean, hover, contours, pixel grid, and vignette.
6. The renderer must not block the simulation loop. GPU uploads happen synchronously through `queue.writeTexture` after each tick.
7. When WebGPU is unavailable, fail clearly; do not silently render a blank map.
8. Device pixel ratio is capped at 2 to bound fill cost.
9. Exact shader results may differ slightly across GPUs; they are presentation only and cannot affect simulation.

## 9. Networking target (summary)

The online design is in [NETWORKING.md](NETWORKING.md). Normative target:

1. The server is authoritative. Clients send **intents**, never ownership or troop values.
2. The server runs the same deterministic simulation at 10 Hz.
3. Clients may run the same simulation locally for prediction and responsive interaction.
4. The server stamps commands with an authoritative tick and orders them deterministically.
5. Clients receive owner-change deltas, public player snapshots, and a periodic checksum.
6. On a checksum mismatch or reconnect, the client requests a baseline snapshot and resynchronizes.
7. The map seed plus map version is part of the welcome/baseline; map pixels are never streamed every tick.
8. Server and client protocol versions must match. Unknown or incompatible versions are rejected.

The wire shape is sketched in `src/lib/game/net/protocol.ts`. No server exists yet.

## 10. Performance requirements

| Area                | Target                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------- |
| Simulation tick     | < 2 ms at p95 in a normal 8-player mid-game (10 Hz budget = 100 ms)                         |
| Render loop         | 60 fps at 1600 × 1000 on integrated GPU hardware; 120+ on discrete                          |
| Dirty uploads       | Typical < 200K pixels/tick; must not upload the full 2.1M pixels per tick under normal play |
| Map generation      | < 500 ms on desktop                                                                         |
| Checksum            | On-demand only; < 20 ms for full map                                                        |
| JS memory           | < 120 MiB additional heap for a live match on desktop                                       |
| Input latency       | Click-to-visible frontier update ≤ 2 ticks                                                  |
| Time to interactive | Map + GPU ready in < 1.5 s after download on a modern desktop                               |

Detailed budgets, methodology, and the current measured baseline are in [PERFORMANCE.md](PERFORMANCE.md).

## 11. Failure handling

| Failure                    | Behavior                                                         |
| -------------------------- | ---------------------------------------------------------------- |
| No WebGPU / adapter        | Error overlay with actionable text; no game starts               |
| Shader compilation error   | Error overlay with compiler text (development aid)               |
| GPU device lost            | Error overlay via callback; simulation is not corrupted          |
| Change-buffer overflow     | Renderer full resync; simulation continues                       |
| Snapshot has invalid pixel | Renderer ignores out-of-range change; full resync path available |
| Map generation error       | Loading transitions to error state with message                  |
| Browser tab suspended      | Driver caps catch-up at 4 ticks; no unbounded spiral             |
| Checksum mismatch (future) | Request full authoritative baseline; never silently continue     |

## 12. Acceptance criteria for the v0.1 slice

- [x] Fresh install: `pnpm install && pnpm check && pnpm test && pnpm build` all pass.
- [x] A seed produces the same map, starts, bot behavior, and checksum in two independent simulation instances with identical commands.
- [x] The human can expand by clicking neutral land next to their frontier.
- [x] The human can attack a rival and capture connected enemy pixels.
- [x] Troops are spent on launch and capture; income and caps are visible.
- [x] Eliminations and a final winner can be reached.
- [x] `Space` freezes the tick counter and the simulation; resuming continues it.
- [x] Camera does not alter simulation state.
- [x] Map updates do not upload the full texture every tick in normal play.
- [x] WebGPU absence produces an error screen rather than a broken canvas.
- [x] Desktop and narrow layouts do not overflow horizontally.
- [x] Documentation matches the implemented rules and known limitations.

## 13. Open design questions

These are intentionally unresolved; decide them with the relevant document.

1. **Fog of war:** Does seeing the whole pixel map make the game more readable, or does hidden territory create better tension? Current: fully visible.
2. **Player count online:** 8 human players, mixed humans + bots, or configurable rooms?
3. **Match duration:** how aggressive should bots and income be for first-time players?
4. **Server tick buffer:** how many ticks of command latency to absorb before "the server decided too late" rejection?
5. **Binary protocol:** protobuf, MessagePack, custom packed buffers, or JSON on a binary WebSocket message? Draft assumes binary-friendly JSON shapes.
6. **Map generation portability:** whether to bake maps into versioned assets with content hashes instead of regenerating them client-side.
7. **Simulation worker:** move simulation to a Web Worker once UI or prediction load grows.
8. **Rendering fallback:** is WebGL2 worth the maintenance cost for unsupported browsers?
